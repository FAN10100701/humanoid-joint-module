# 串口调试助手 · 能力评估与优化路线图

> 评估基准：SerialLab V2.2.1（站点 V2.2.1，2026-10-14）  
> 评估方式：通读 14 个模块共 8525 行源码 + 对照主流同类工具能力面 + 实测数据管线上限  
> 对象：`06_学习工具/_串口调试助手/`，入口页 `06_学习工具/21_串口调试助手.html`

---

## 0. 结论先行

1. **一句话定位**：在**主线能力**（文本/HEX 字段解析 → 实时绘图 → 录制导出）上已达主流水平，并有**两处超出同期工具**（AI 调试包、解析内核可被 Node 直接复用）；但在**四条支线**（工业协议栈 / 脚本化 / 长时无人值守记录 / 闭环自动化）上明确落后于 VOFA+、Serial Studio 与专业桌面工具。当前正确定位&#x662F;**「教学 + 轻量调试 + 可二次开发的基座」**，不是「生产级协议分析仪」。
2. **人 vs AI 的短板方向完全不同**：
   - 给**人**用的短板集中在「**记录时长**」与「**会话复盘**」（原始记录只有 5000 条，波形不能导出成图）。
   - 给**AI**用的短板集中在「**数据出不了浏览器**」（唯一通道是人手动下载 JSON 再粘贴）。
3. **最高性价比的三件事**（都在本路线图 P0 内）：
   - ① 统一并提高原始记录上限——**当前不到 10 行代码**；
   - ② 波形可导出 PNG——写报告、给 AI「看图」的刚需，当前完全缺失；
   - ③ 本地串口桥——让 AI 能自己开串口，是**闭环自动化的地基**，其余自动化都建在它之上。

### 1.2 已达标甚至超出的部分

| 项       | 证据                                                                                      |
| ------- | --------------------------------------------------------------------------------------- |
| 错误零崩溃   | `parser.parseHexFrame` 任何越界都返回 `ok:false` + `reason`，不抛异常；`core.emit` 单个监听器抛错被兜住不打断数据管线 |
| 分帧兜底完整  | 帧头+长度字段 / 帧尾定界 / **静默超时切帧**（`transport.lingerDot`）三路并存，裸流也能收                            |
| 竞态处理    | `transport` 用递增 `epoch` 让旧读循环自认过期；`reopen()` 内置 250ms 去抖；释放顺序固定                         |
| 传输护栏    | 硬流控与手动 RTS 互斥告警、DTR 复位窗口禁发（`resetWaitMs`）、自动发送全局限流、触发应答冷却                               |

### 1.3 具体短板（含本次新发现的真实缺陷）

#### ★ 短板 1（**真实缺陷，建议立刻修**）：两套记录上限打架，AI 只能看到 1/4

| 项  | 事实                                                                                                                                                               |
| -- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 现象 | UI「显示」页与调试包摘要都写「自动存档上限 **20000** 帧」；但 AI 调试包的 `samples`、原始 CSV/TXT 导出、文本监视器、缓存重放**全部源自 `datastore.recentRaw()`**，而该缓冲区硬上限 `RAW_CAP = 5000`（`js/datastore.js:37`） |
| 根因 | `ui.recordCap`（20000，`js/core.js:160`）只驱动 `Timeline.setMaxFrames`（录制帧，`js/app.js:502`）；**原始字节记录是另一套 FIFO**，从未跟随该配置                                               |
| 影响 | 50Hz 下原始记录只覆盖 **100 秒**。做一次 10 分钟电机温升/纹波测试，前 9 分钟对 AI 与导出**不可见**；且用户按 UI 认知以为有 20000 帧，实际少 75%——**属"文档/UI 与实际不符"性质**                                             |
| 附带 | `app.replayBuffered()` 默认参数也写死 5000（`js/app.js:456`），同样受限                                                                                                        |
| 建议 | 把 `RAW_CAP` 提为可配置（跟随 `ui.recordCap`），或至少让 UI 与调试包按**真实生效值**显示。工作量：< 10 行 + 1 条断言                                                                                 |

#### 短板 2：无 Modbus RTU/ASCII

只有 `crc16modbus` 一个校验变体，没有任何 Modbus 帧语义（功能码/寄存器/从站地址/异常码）。电机驱动器、PLC、伺服几乎默认走 Modbus → 这是**工业场景最大的一道墙**。

#### 短板 3：校验和族不全

仅 `none / sum8 / xor8 / sum16 / crc16modbus`（`js/codec.js:352`）。缺 `crc8`（Dallas/MAXIM）、`crc16-CCITT/IBM`、`crc32`、`bcc`、`fletcher`。国产开发板与传感器大量使用 `crc16-CCITT`。

#### 短板 4：无脚本引擎，表达力有天花板

只有**声明式字段表 + 表达式**（`expr.js` 安全求值）。无法表达：变长 TLV、嵌套结构、位域打包（`bits` 字段）、状态机解析、跨帧累积量。VOFA+/Serial Studio 都提供 JS 脚本钩子——但**本项目故意不给执行权限**（安全边界：面板包会互相分享，允许执行代码 = 导入配置变 XSS 后门）。因此正确解法不是加 eval，而是**扩充声明式能力**（见 6. 优先级表 P1）。

#### 短板 5：无法导出波形图片

全代码库无 `toDataURL` / `toBlob` / `image/png`。写报告、给 AI 看趋势、贴到群里——**只能截屏**。对「人写文档」和「AI 读图」都是硬伤。

#### 短板 6：无游标测量

没有 mark/cursor 区间测量，没有 ΔT/ΔV、峰峰值、RMS、THD。电机调试要看**超调量、稳态纹波、转矩脉动**，缺这组指标就只能靠肉眼。

#### 短板 7：无多串口并行

单 `SerialPort` 实例。`navigator.serial.getPorts()` 已授权多口，但 UI 只有一个连接位。双 MCU 对拖、主从联调场景无法覆盖。

#### 短板 8：无文件发送

不支持「把 .bin/.hex/.csv 当数据源循环发」，也没有分块发送与进度。烧写辅助、压力测试、协议一致性测试都缺工具。**新增时注意长度上限提示与分批节流。**

#### 短板 9：重连后时间轴连续性无保证

断线重连后 `t`（`performance.now`）继续走，波形 X 轴会出现一段空白或跳变，且没有「断点标记」。长测复盘时容易误读。

#### 短板 10：性能无压测基线

只有 `ui.drawInterval` 节流（16~200ms）与环形缓冲（通道 30000 点/条、原始 5000 条）。**没有速率基准数据**：115200（≈11.5KB/s）下 7 个面板同开是否掉帧？1Mbps 下分帧是否会积压？无法回答，也就无法承诺「稳定跑通」。

### 1.4 稳定性分层评价

| 层次     | 评价     | 说明                                |
| ------ | ------ | --------------------------------- |
| 算术/解析层 | **A**  | 纯函数、零异常契约、126 项断言锁死边界             |
| 传输层    | **A−** | 竞态与资源释放做得比多数桌面工具细；缺断点标记           |
| 数据层    | **B**  | 环形缓冲设计正确，但两套上限打架（短板 1），长时记录能力弱    |
| 渲染层    | **B+** | DPR 适配、节流、跨槽重建都处理了；无游标测量、无图片导出    |
| 协议层    | **C**  | 仅"通用字段表"，无任何工业协议栈                 |
| 自动化层   | **D**  | 无外部接口、无脚本、无落盘——**这是与专业工具差距最大的一层** |

**结论**：**"稳"已经稳了**（不会崩、不会卡死、不会算错），差的&#x662F;**"久"（长时记录）与"通"（对外接口/协议）**。

## 二、以"实际调试者"视角的改进建议

按我在调试固件/电机时**真实被卡住的顺序**排序（不是按实现难度）。

| #  | 摩擦点（现状）                    | 期望                                   | 为什么排这么前                          |
| -- | -------------------------- | ------------------------------------ | -------------------------------- |
| 1  | 想让我看数据，得**点两次下载 + 手动粘进对话** | 一键「复制为 AI 提示词」，或直接落到本地文件（见第三节）       | 这是当前协作链路上最大的时间黑洞                 |
| 2  | 失败行只标红，**不说什么错**           | 行尾内联原因：`✗ 校验和 expect=F1 got=4B`      | 标红只告诉你"有问题"，不告诉你"哪有问题"           |
| 3  | 冻结后**不能框选统计**              | 拖选区间 → `min/max/avg/σ/RMS/峰峰值/纹波`    | 电机调试的**核心指标**全靠这个，现在得导出 CSV 再自己算 |
| 4  | 通道有 `unit` 字段但**界面没用起来**   | Y 轴显示单位、支持单位换算（mA↔A、rpm↔rad/s）       | 省掉每次心算与标注                        |
| 5  | X 轴只有相对秒                   | 可切：相对秒 / 绝对时刻 / **采样序号**             | 与固件里的 `tick` 对齐才能定位到代码行          |
| 6  | 每次都从零拖面板                   | 内置**电机调试模板**：电流环/速度环/位置环三联 + 转矩-转速双联 | 关节模组调试的高频组合，一次到位                 |
| 7  | 鼠标流为主                      | `Ctrl+K` 命令面板（连接/套预设/加面板/导出）         | 高频操作键盘化，效率翻倍                     |
| 8  | 想求助得口述配置                   | 把「规则+面板+采样」编码进 URL hash，一键分享         | 教学场景（学生问你"为什么解不出来"）极其有用          |
| 9  | 演示数据太"干净"                  | 可注入**丢帧/校验错/粘包/乱码**                  | 排错是教学目标，干净数据教不会学生                |
| 10 | 打印速度只能"降"不能"追"             | 除节流外，加「高速跟随到底部」开关                    | 高速流下现在只能靠拖滚动条                    |

## 三、面向 AI Agent 调试硬件：能否省去复制粘贴

### 3.1 自动化程度分级与本应用现状

| 级别     | 含义                                | 本应用                                    |
| ------ | --------------------------------- | -------------------------------------- |
| L0     | AI 看不到数据                          | —                                      |
| **L1** | **数据能被 AI 读懂，但搬运靠人**（下载/粘贴）       | **← 当前在这里**（`debugBundle` 结构完备，但出口是人手） |
| L2     | AI 能**直接读到**数据（文件/接口），无需人搬运       | 未实现                                    |
| L3     | AI 能**直接控制**串口（开关/收发/改规则）         | 未实现                                    |
| L4     | AI 能在此之上**自主迭代**（读→判→改→烧→再跑，见第五节） | 未实现                                    |

`debugBundle()` 已经把「AI 读得懂」这件事做完了——`frameLayout` / `channels` 统计 / `failures` 带原因 / `hints` 主动提示 / 纯文本 `brief`。**瓶颈只剩"怎么把它交给 AI"**。

### 3.2 先排除一条死路

> **浏览器内的 Web Serial 无法被 AI 自动化。** `requestPort()` 必须在**真实用户手势**的调用栈里，且端口选择是浏览器原生弹窗——AI 既不能点，也不能授权。这是平台安全红线，**不要试图绕过**（用扩展注入、模拟点击等都属于脆弱且违规的做法，且 `file://` 下根本没有串口）。

所以正确架构是**双轨**：

```
给人用：浏览器子应用（今天的 SerialLab，交互、看图、教学）
给 AI 用：本地串口桥（新，CLI/接口）
共用：同一份解析内核 —— 靠 14 个模块已有的 UMD 尾在 Node 里 require 真源
```

> 这条「共用内核」是本项目一个**被低估的资产**：`parser.js` / `codec.js` / `core.js` / `expr.js` 都能在 Node 里直接 `require`，所以**AI 解析出的结果与你在浏览器里看到的逐字节一致**，不会出现"两边算法不一样"的信任问题。

### 3.3 三个方案

| 方案                       | 做法                                                                                                                         | 人是否需在场           | 工作量   | 风险/前提                                                  |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------- | ---------------- | ----- | ------------------------------------------------------ |
| **A. 浏览器 HTTP 上报**       | 子应用加一个可关的开关：把每次/定时的 `debugBundle` `POST http://127.0.0.1:7788/ingest`；配 `_本地工具/serial-inbox.mjs`（约 30 行）落盘到固定目录            | 需人开着页面并连上设备      | 1 天   | 浏览器 CORS/混合内容需处理；仍是"人在前半程"                             |
| **B. 本地串口桥（推荐）**         | `_本地工具/serial-bridge.mjs`（Node + `serialport`）：`open/read/write/parse/log` 子命令，**直接 require 子应用内核**解析；输出 JSON 到 stdout 或文件 | **不需要**（AI 独立收发） | 2~3 天 | 引入 npm 依赖——但**只在 `_本地工具/`**，不违背站点"零依赖"约束（该目录本就在部署白名单外） |
| **C. 把 B 包成 MCP server** | 暴露 `serial_open / serial_write / serial_read / serial_parse / serial_log` 工具                                               | 不需要              | +1 天  | 需要 agent 侧配置 MCP；一次配好，**以后任何会话都能直接调**                  |

**推荐路线：先 A（快速见效）→ 再 B（真正的自动化）→ 最后 C（接口化）。**  
C 一旦落地，你的诉求「不用我来回切换复制粘贴」就彻底解决：Agent 调 `serial_read --ms 2000 --json` 拿到结构化结果，直接分析、直接改代码。

## 五、自动调试闭环：读 → 判 → 改 → 烧 → 再跑

这是你诉求的终点：「根据串口输出自动调试代码、绘制波形并反复迭代」。可行，但要拆开看**哪一段已经通了、哪一段必须新建**。

### 5.1 目标循环

```
      ┌──────────────────────── 迭代 n ────────────────────────┐
      │                                                        │
 [1] 烧录固件 ──→ [2] 复位运行 ──→ [3] 采数据 ──→ [4] 解析+判定 │
 (OpenOCD/CLI)     (DTR/命令)      (串口桥)      (复用内核)     │
      ↑                                              │        │
      │                                              ↓        │
      └──────────── [6] 改代码/参数 ←── [5] AI 分析（读 JSON+图）┘
```

### 5.2 落地五步（每步都能独立验收）

| 步      | 做什么                                                                                                                                | 依赖               | 验收                            |
| ------ | ---------------------------------------------------------------------------------------------------------------------------------- | ---------------- | ----------------------------- |
| **S1** | **读+解析+判定**：`serial-bridge.mjs read --ms 3000 --rule '{"...}' --json`；`assert` 子命令做阈值判定（`--expect "rpm>1750" --settle-time<300ms`） | 方案 B             | 一条命令拿到结构化样本 + pass/fail + 指标  |
| **S2** | **留痕**：每轮落 `trial-<n>.json` + `trial-<n>.png`（波形图）                                                                                 | 短板 5（PNG 导出）必须先补 | 任意两轮可 diff（超调/稳态误差/纹波三列）      |
| **S3** | **烧录自动化**：`flash.cmd`（STM32CubeProgrammer / OpenOCD CLI）                                                                           | 你本机工具链           | `flash && run_trial` 一条命令跑完一轮 |
| **S4** | **参数在线化**：固件支持 `set kp=1.2` / `get` 命令；AI 调参**不重烧**                                                                                | 固件改一点            | 调参一轮从"分钟级"降到"秒级"              |
| **S5** | **接回 MCP**：把 S1~S3 包成工具，Agent 自主循环                                                                                                 | 方案 C             | Agent 一句话跑 20 轮并给收敛曲线         |

> **关键判断**：S4 的收益远大于 S3。因为「重烧一轮 ≈ 十几秒到一分钟」，而「串口改参数一轮 ≈ 1 秒」。**先把参数做成可在线读写**，迭代次数才能上去（自动整定需要几十上百轮）。


### 5.3 风险与边界（必须先说清）

| 风险                 | 说明                         | 对策                                                       |
| ------------------ | -------------------------- | -------------------------------------------------------- |
| **浏览器路线做不到闭环**     | Web Serial 的授权模型决定 AI 无法接管 | 走本地桥，别在浏览器里硬啃                                            |
| **判定指标要先定义**       | "这轮好还是坏"没有客观标准，AI 会瞎调      | 先把指标写进 `expect`（超调/稳态误差/上升时间/纹波），不达标即 fail               |
| **烧录是危险动作**        | 自动烧写可能把板子刷成砖               | 烧录步骤**必须人工确认**，且先备份原固件；AI 只自动跑"读+判"                      |
| **长时测试被 5000 条截断** | 短板 1 会直接毁掉整晚的测试数据          | **先修短板 1**，再谈长时间迭代                                       |
| **安全边界不能破**        | 为了脚本化而引入 `eval` 会让配置分享变成后门 | 只扩声明式能力（位域/TLV/变长），坚持不执行用户代码；桥在本地工具目录用 Node 原生能力，不进浏览器产物 |

### 明确**不建议**做（写下来免得以后反复讨论）

1. **在浏览器里引入 `eval` / `new Function` 做脚本解析** —— 配置会被互相分享，等于开 XSS 后门。要表达力就扩声明式能力。
2. **试图自动化浏览器内的端口选择弹窗** —— 违反平台安全模型，脆弱且不可持续；直接走本地桥。
3. **引入 CDN 上的 JS 库（含 Chart.js / three.js）** —— 破坏"零依赖、可离线、可单文件拷走"这条命根子，FFT/CRC/表达式都是自研的，保持这个状态。
4. **把子应用版本绑到站点 `S.VERSION`** —— 它是可独立拷走的基座，绑上去就失去独立性。
