## 二、三种权限模式

| 模式 | 权限 | 适合 |
| --- | --- | --- |
| **A. 公开 + Fork/PR** | 零权限,任何人可 Fork 后提 PR,由维护者 review 合并 | 全班同学,最安全,推荐起步 |
| **B. Collaborator** | 受邀同学获得 **Write** 权限,可 push 到 master | 少数信任的核心同学,需配合分支保护 |
| **C. GitHub 组织** | 建组织 + Team 按角色批量授权 | 10 人以上或长期项目 |

**本站推荐组合**:全班走 **模式 A**(Fork/PR)+ 核心同学加 **模式 B**(Collaborator),并开启 **master 分支保护**。既安全又高效。

## 三、安全红线(每个同学必须遵守)

1. **严禁 `git add -A` / `git add .`** —— 只 `git add 指定文件`。历史事故:一条 `add -A` 把协作者半成品卷进提交。
2. **绝不提交**以下个人/隐私内容(已在 `.gitignore`,勿用 `git add -f` 强加):
   - `_视频素材/`(含浏览器 profile 等隐私数据,已移出仓库)
   - `.trae/`、`.zcode/`(开发工具目录)
   - 一次性临时文件(`校验*.js` 等)
   - 未完成的个人功能页(写完后由维护者显式提交)
3. **🔒 AI API Key 纪律(最高危新泄漏面,2026-08-28 增补)**:站内「AI 答疑助手」使用 DeepSeek/豆包等付费 API——**严禁把任何 API Key(sk-…、ep-… 等)写进代码、文档、Issue、PR 描述、聊天截图或 commit 信息**。Key 只保存在每个人自己浏览器的 localStorage(见 `06_学习工具/13_AI答疑助手.html`),换电脑需重新填写。发现泄漏立即:①作废该 Key ②在 Issue 里只说"有泄漏"不带 Key 内容。
4. **版本号四处同步**:`_assets/site.js`(S.VERSION)、`index.html`、`CHANGELOG.md`、`sw.js`——漏一处自检就 FAIL。
5. **新页面落地要"登记五件套 + CHANGELOG + 尽早广播"**:page-meta.js / search-index.js / sitemap.xml / 学习地图 / index.html(卡片+SITE_SECTIONS),否则自检报 "not in index"。
   - **谁执行登记**:**人类协作者**走 PR 可直接改上述登记文件(CI 自检把关);**AI 协作者一律不改公共登记文件**,在完成报告中列出"需要主代理登记"清单,由主代理统一落账(避免并发冲突)。
6. **中文文本用「」引号**,禁止 ASCII 双引号包中文(历史事故曾导致全站 JS 崩溃)。
7. 涉及数字/型号/参数必须核实,不确定标「待核实」,不得编造。

## 三·五、多协作者「认领与广播」机制(2026-08-28 正式化)

多人/多 AI 并行开发时按此执行,避免互相覆盖:

1. **认领**:动手前在 Issue 或群里声明"我要改 XX 板块的 XX 页",**按板块认领**;同一文件同一时间只应有一个人在改。
2. **广播**:新建页面文件落地后**立即广播**(哪怕正文未完),让协作者避开翻页链/索引的断链窗口。
3. **完成报告格式**(AI 协作者必填):`改动文件清单(逐个列出)+ 行数 + 需要主代理登记的条目 + 是否动了缓存页(是→必须 bump sw.js CACHE)`。
4. **冲突处理**:编辑工具提示 "file changed since it was read" = 有人在改 → 重读再改,禁止强行覆盖。
5. **动画/缓存页纪律**:改任何被 sw.js PRECACHE 或 3D sw 缓存的页面,必须同步 bump 对应 CACHE 名,否则用户端永远吃旧文件——这是历史上"改了动画没生效/时好时坏"的根因。

## 四、master 分支保护设置(维护者操作一次即可)

> 目的:即使给同学加了 Collaborator,也不能直接推坏 master;所有改动走 PR + CI 通过。

1. GitHub 仓库 → **Settings → Branches → Add branch protection rule**
2. Branch name pattern 填 `master`
3. 勾选:
   - ✅ **Require a pull request before merging**(禁止直接 push 到 master)
   - ✅ **Require status checks to pass before merging** → 选中 `self-check`(CI 自检必须通过)
   - ✅(可选)**Require approvals** = 1(至少一人 review)
4. 保存

## 五、加入步骤(保姆级)

### 前提:注册 GitHub
没有账号的同学先去 `github.com` 注册(免费,2 分钟)。仓库地址:
`https://github.com/FAN10100701/humanoid-joint-module`

### 方式 A:全班走 Fork + PR(零权限)
```
1. 打开仓库 → 右上角 Fork(复制一份到自己名下)
2. git clone https://github.com/<你的用户名>/humanoid-joint-module.git
3. 本地改代码
4. git add 指定文件 && git commit -m "feat: ..." && git push
5. GitHub 上回到原仓库 → Pull Requests → New Pull Request → 描述改动
6. 维护者 review 后合并
```

### 方式 B:核心同学被邀请为 Collaborator(直接 push)
```
1. 维护者在:仓库 → Settings → Collaborators → Add people → 输入你的 GitHub 用户名 → 发邀请
2. 你在 GitHub 通知/邮箱里点接受
3. git clone https://github.com/FAN10100701/humanoid-joint-module.git
   (或已有 clone 则 git pull 最新)
4. 改 → git add 指定文件 → git commit → git push origin master
   (注:开了分支保护后,push master 会被拒,需走 PR)
```

### 首次协作练习(建议每人先跑通)
改一个现有页面的错别字/补一条参考来源 → 提交 → 提一个 PR → 维护者合并 → **全流程跑通**。
